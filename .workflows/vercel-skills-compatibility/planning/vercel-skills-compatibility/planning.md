# Plan: Vercel Skills Compatibility

## Phases

### Phase 1: Skills install as skills, under their declared names
status: draft

**Goal**: `add` reads each skill's SKILL.md frontmatter and installs it as Vercel names it. A skill folder (even one carrying its own `agents/`) installs as a skill, into a folder named by its sanitized declared name, under exactly one manifest key however it was selected.

**Why this order**: Declared-name identity and the skill-versus-plugin classification are the model every later phase selects against, displays, migrates and prints. Doing this first also fixes the most damaging breakage: a skill carrying `agents/` silently becomes subagents and is lost. It works on today's one-level membership scan, so it stands alone.

**Acceptance**:
- [ ] Given a repo whose member folder `taste-skill` has a SKILL.md declaring `name: design-taste-frontend`, when it is picked from the `add` menu for Claude, it lands in `.claude/skills/design-taste-frontend/` under manifest key `owner/repo/design-taste-frontend`, and a later `update` reinstalls it from `taste-skill` into the same folder
- [ ] Given a skill whose SKILL.md has no frontmatter, no string `name`, YAML that fails to parse, or a non-YAML fence, when it is added, it installs under its folder name with no warning
- [ ] Given a skill folder holding SKILL.md beside `agents/` (e.g. `agents/openai.yaml`), when it is added, the whole folder including `agents/` lands in the agent's skills directory, nothing is written to `.claude/agents/`, and the manifest records a skill
- [ ] Given a folder holding SKILL.md beside `skills/` and `agents/`, or SKILL.md beside `agents/` with `agntc.json` declaring `"type": "plugin"`, when it is added, it installs as a plugin with its agents routed to `.claude/agents/` and the root SKILL.md not installed
- [ ] Given skills declaring `../x`, `My Skill!!` and `---`, when each is installed, they land in `x`, `my-skill` and `unnamed-skill` inside the agent's skills directory and never outside it
- [ ] Given a skill installed from the menu, when the same skill is re-added through a GitHub tree URL to its folder, the manifest still holds one entry under `owner/repo/<folder>`
- [ ] Given a skills-only repo whose `skills/foo/` holds `agents/` and no SKILL.md, when it is picked from the menu, it installs whole under key `owner/repo/skills/foo`
- [ ] Given a repo with a root SKILL.md declaring `name: foo-skill`, when it is added, it installs into `.claude/skills/foo-skill/` under key `owner/repo`
- [ ] Given a declared name containing terminal escape sequences, when `add` prints it, escapes and control characters are stripped; given frontmatter using a YAML tag that would construct an object or run code, the skill installs and nothing in it executes
- [ ] Given existing plugin, root-skill and collection sources, when they are added and updated, they behave as before apart from folder naming
- [ ] Given a member folder holding SKILL.md beside `skills/` and `agents/`, or SKILL.md beside `agents/` whose own `agntc.json` declares `"type": "plugin"`, when it is picked from the menu or named by a tree URL, it installs whole as a plugin member keyed `owner/repo/<path>`; given a member holding SKILL.md beside `skills/` alone whose own `agntc.json` declares `"type": "plugin"`, it bundles that `skills/` as one member and leaves its SKILL.md out
- [ ] Given a skill whose `name` is an empty string, it installs under its folder name; given a `name` that is only whitespace, it installs into `unnamed-skill`; given a `name` with line breaks or surrounding whitespace, it is shown and matched with line breaks as spaces and the whitespace trimmed
- [ ] Given a plugin whose `skills/` nests skills in category folders and also holds a loose `README.md`, when it is added, each skill installs flat in its declared-name folder, the README is not installed, and the output names it as left out

### Phase 2: Discovery finds skills where Vercel's does
status: draft

**Goal**: `add`'s menu offers every skill Vercel's discovery would find: category-nested skills, `.curated`/`.experimental`/`.system`, agent directories, plugin manifests, the five-level fallback and `--full-depth`. Plugin members are offered whole and internal skills are hidden. Installables that would share a name, install folder or key are offered once, first in priority order. A source with nothing installable is refused.

**Why this order**: Extends Phase 1's skill model to every place Vercel looks. Deduplication by declared name and install folder, and the internal flag, come from Phase 1's frontmatter reading and sanitizing. Bundles, selection and the pre-install summary all build on the member set discovery produces.

**Acceptance**:
- [ ] Given a category-nested repo (`skills/<category>/<skill>/SKILL.md`, the shape of `mattpocock/skills`), when `add` runs, the menu offers every skill by declared name and a picked skill installs flat in its own folder (today: "Cancelled — no plugins selected", exit 0)
- [ ] Given skills only under `skills/.curated/`, under one of Vercel's agent directories such as `.claude/skills/`, or in a directory declared in `.claude-plugin/marketplace.json`, when `add` runs, the menu offers them
- [ ] Given a source whose own `skills-lock.json` records a skill in its own `.claude/skills/`, when `add` runs, that skill is not offered
- [ ] Given a source whose search roots find nothing and whose only SKILL.md sits four folders deep, when `add` runs, the fallback walk offers it; given `--full-depth` on a repo with a root SKILL.md and nested skills, the menu offers the nested skills (including one nested inside another skill's folder) instead of installing the root as a single skill, and the root SKILL.md is offered beside them as a skill of its own, keyed `owner/repo`
- [ ] Given two skills declaring the same name, or declared names that collide only once sanitized (`Foo Bar` and `foo-bar`), the menu offers only the one first in priority order; given `skills/build/SKILL.md`, it is offered; skills reachable only through `node_modules/` or a symlinked directory are not
- [ ] Given a top-level plugin member `foo/` and `skills/bar/SKILL.md` declaring `name: foo` (both would key `owner/repo/foo`), when `add` runs, the menu offers the member and not the skill
- [ ] Given a non-hidden folder with `skills/`, `agents/` or `hooks/` and no SKILL.md, the menu offers it as one entry and picking it installs it whole with agents and hooks routed; nothing under `.git/` is ever offered; given a tree URL naming such a folder (including a skills-only pack), it installs that member whole without a menu
- [ ] Given a skill whose frontmatter sets `metadata.internal: true`, it is absent from the menu; given search roots holding only internal skills, the fallback walk still runs; given a source whose only skills are internal, `add` naming no skill is refused as finding nothing installable; given an internal root SKILL.md, `add` naming no skill does not install it and offers what the search roots find; given `skills/tools/SKILL.md` marked internal with `skills/tools/helper/SKILL.md` below it, `helper` is not offered by the search-root walks
- [ ] Given a source where discovery finds nothing installable, when `add` runs, it exits non-zero, writes nothing, and says nothing installable was found
- [ ] Given a skill installed from a category-nested repo, when `update` runs after the source changes, it reinstalls from that skill's folder
- [ ] Given a folder the deeper walks reach that holds SKILL.md but is a plugin member under §5.1's rules (SKILL.md beside `skills/` and `agents/`/`hooks/`, or beside `agents/`/`hooks/` or `skills/` alone with its own `"type": "plugin"`), the menu offers it whole, keyed by its path, and nothing inside it is offered separately
- [ ] Given two skills declaring the same name in different places, the menu offers the one the walks reach first: a search root listed earlier over a later one, the search roots over the fallback walk, and within one walk depth-first with folders in name order (`skills/a/x/foo` over `skills/b/foo`), whatever order the filesystem lists folders in

### Phase 3: `--plugin` bundles everything discovery finds
status: draft

**Goal**: `--plugin` and `"type": "plugin"` bundle a whole source as one entry. Every discovered skill installs flat in its own folder, internal skills included. Plugin members' skills, agents and hooks are routed to their places, and no two of the bundle's installables write the same path. The bundle installs within every ceiling it holds, refuses only the shapes §6.6 refuses, and works out its contents again on every update.

**Why this order**: A bundle is defined as every skill discovery finds, so this follows Phase 2 directly, and it leaves out colliding member content by Phase 2's priority order. It fixes what a bundle holds before Phase 4 migrates installs onto it and before Phase 8 decides how picks meet bundles.

**Acceptance**:
- [ ] Given a category-nested skills-only repo, when added with `--plugin`, the manifest gains one entry, every discovered skill (internal ones included) lands flat in its own declared-name folder, and no category folder appears in any agent's skills directory
- [ ] Given a tree URL to one category folder with `--plugin`, the bundle holds only that folder's skills
- [ ] Given a source with plugin member folders at its top level (today refused "collection of N members — cannot bundle"), when added with `--plugin` or with `agntc.json` declaring `"type": "plugin"`, it installs as one entry with each member's skills in the skills directory, agents in `.claude/agents/` and hooks in `.claude/hooks/`
- [ ] Given a source where a top-level member and a member under `skills/` each ship `agents/reviewer.md`, when added with `--plugin`, the top-level member's `reviewer.md` is installed and the output names `reviewer.md` and the member under `skills/` as left out; given a loose skill installing into `x` ahead of a member whose `skills/x/` also lands in `x`, the loose skill's copy is installed and the output names the member's `x` and that member
- [ ] Given a bundle in which one member's or one skill's own `agntc.json` restricts to Claude, the agent prompt offers Claude alone (auto-selected when Claude is detected) and the bundle installs for Claude only; given a plugin whose `skills/` holds a Claude-only skill or member, the plugin installs for Claude only
- [ ] Given a lone root SKILL.md, or a root SKILL.md beside `agents/` with no `"type": "plugin"`, when added with `--plugin`, the command exits non-zero, writes nothing and names the refusal; given a root SKILL.md beside `skills/` alone, `--plugin` bundles the skills under `skills/` without the root SKILL.md; given a plugin, `--plugin` changes nothing
- [ ] Given an installed bundle whose source has since gained one skill and lost another, when `update` runs, the new skill is installed, the removed skill's files are gone, and the manifest still holds one entry
- [ ] Given a plugin or bundle two of whose own skills would take the same install folder, the first in priority order installs and the output names the one left out
- [ ] Given a source whose only skills are internal, when added with `--plugin`, it bundles them rather than being refused; given search roots holding only internal skills, the bundle does not take skills only the fallback walk reaches
- [ ] Given a bundle whose source's `skills/` holds a loose `README.md`, the output names it as left out; given a bundle of a source with no `skills/`, its root README, licence and package files are not named; given a path naming a folder that holds no `skills/`, that folder's loose files are named
- [ ] Given a plugin that ships `agents/reviewer.md` and has a member under its `skills/` also shipping `agents/reviewer.md`, the plugin's own `reviewer.md` is installed and the output names the member's copy and that member as left out
- [ ] Given a bundle made from top-level skill folders (no `skills/`, `agents/` or `hooks/` at its root), when `update` runs, it reinstalls as one entry; given a bundle whose source now holds nothing the bundle takes, `update` stops that entry with its install intact, says why, other entries proceed, and the command exits non-zero
- [ ] Given `--plugin --full-depth`, or `--full-depth` on a source whose `agntc.json` declares `"type": "plugin"`, the command exits non-zero, writes nothing, and names the two as not combining; given `--plugin` with a tree URL to `skills/frontend/`, the bundle is keyed `owner/repo/skills/frontend`

### Phase 4: Existing installs move to their new shape

### Phase 6: Repository identity across forms and hosts
status: draft

### Phase 7: `@` selects skills; versions move to `#`
status: draft

**Goal**: `@` and `-s/--skill` select skills by declared name: case-insensitive and exact, `'*'` for all, internal skills when named. `#` carries constraints, tags and branches, including `#ref@skill`. A bare add falls back to the default branch when the newest tag lacks the pick. Any unmatched name refuses the whole line and lists what's available.

**Why this order**: `@` can only become a skill selector once there are declared names to match (Phases 1–2) and path forms to list plugin members by (Phase 5). The version suffix moves to `#` in the same phase so no version line, and no upgrade advice agntc prints, is left without an accepted form.

**Acceptance**:
- [ ] Given a repo whose folder `taste-skill` declares `design-taste-frontend`, when `add owner/repo@Design-Taste-Frontend` runs, that skill alone installs with no member prompt
- [ ] Given `add owner/repo@a --skill b c`, exactly `a`, `b` and `c` install as separate entries; given `--skill '*'` on a skills-only repo, every non-internal skill installs as its own entry; given `--skill <internal-skill>`, that internal skill installs
- [ ] Given `owner/repo#^1.0`, the best matching tag installs and `^1.0` is recorded; `#v2.0.0` installs that tag with no constraint; `#main` installs that branch; `owner/repo#v2.0.0@skill` installs that skill at that tag
- [ ] Given `owner/repo@v2.0.0` or `owner/repo@^1.0` where no skill has that name, the command exits non-zero, installs nothing, and points at `owner/repo#v2.0.0`
- [ ] Given `--skill nope`, the command exits non-zero naming `nope` and listing the skills the source offers, with plugin members shown as `owner/repo/<path>`; given `--skill real nope`, nothing installs and the message lists `nope` with the alternatives
- [ ] Given a bare `add owner/repo@new-skill` where the newest tag lacks `new-skill` but the default branch has it, it installs from the default branch, says so, and records no constraint; the same holds when the newest tag holds nothing installable
- [ ] Given an exact-pinned entry with newer tags, when `update` prints its upgrade advice (single key or all-mode), the version appears after `#`, never after `@`
- [ ] Given a repo whose root SKILL.md is internal, `add owner/repo@<its name>` (or `--skill <its name>`) installs it as the single skill keyed `owner/repo`

### Phase 8: Picks and "all" meet units
status: draft

**Goal**: Vercel's selection meets agntc's units. "All" never splits a unit, and across an "all" run's entries, a member's skill, agent or hook that lands on a path an earlier installable takes is left out and named. A named pick or a path that lands inside a unit installs that skill alone, with a warning naming what's left out, within the unit's ceiling. `"type": "plugin"` and `--plugin` refuse a named pick.

**Why this order**: Picks need name selection (Phase 7) and path forms (Phase 5). This phase defines how those picks meet the units and bundles settled in Phases 1–3, and applies Phase 3's same-path rule across separate entries.

**Acceptance**:
- [ ] Given a plugin source, or one declaring `"type": "plugin"`, when added with `--skill '*'`, the whole unit installs as one entry with its agents and hooks
- [ ] Given a menu mixing loose skills and plugin members, when added with `--skill '*'`, each skill installs as its own entry and each plugin member installs whole
- [ ] Given a menu where a top-level member and a member under `skills/` each ship `agents/reviewer.md`, when added with `--skill '*'`, each member installs as its own entry, the top-level member with `reviewer.md` and the other without it, and the output names `reviewer.md` and that member as left out
- [ ] Given `owner/repo@x` where `x` sits inside a plugin or plugin member that declares no `"type": "plugin"`, `x` alone installs as a skill, a warning names the agents, hooks and other skills left out, and the agent prompt offers only the unit's ceiling
- [ ] Given the same pick when the unit's `agntc.json` declares `"type": "plugin"`, the command exits non-zero, installs nothing, and names the whole-unit install instead
- [ ] Given a path landing inside a unit (`owner/repo/skills/x`, a tree URL to that folder, or `owner/repo/skills`), it installs as a pick with the same warning and is refused when the unit declares `"type": "plugin"`; with `--plugin`, a path at one skill is refused while a path at a folder of skills bundles that folder
- [ ] Given `--plugin` with `--skill x` or `@x`, the command exits non-zero naming the conflict; given `--plugin` with `--skill '*'`, the whole bundle installs
- [ ] Given two plugin members that both ship `agents/reviewer.md`, both picked from the menu, the member earlier in priority order installs `reviewer.md`, the other installs without it, and the output names what was left out and the member it came from
- [ ] Given a member installed less than whole because another entry from the same repository holds `agents/reviewer.md`, when `update` runs, it leaves out the same path while that entry holds it, names it again and never treats it as in the way; once no entry holds it, the next update installs it

### Phase 11: Unattended `add`
status: draft

**Goal**: `add` runs without prompts under `-y` or when a detected AI agent is the caller. Anything in a unit's way, including an install from another repository holding its key, stops that unit unless `--overwrite` is given. A prompt that cannot be shown refuses the command before anything opens, naming what answers it.

**Why this order**: `-y` answers the prompts that are complete as of Phase 10, and targets detected agents within Phase 9's ceilings. Its clash handling covers every clash already in place, including Phase 6's install from another repository onto a held key. The no-terminal refusal can only name what answers each prompt once the full prompt set exists.

**Acceptance**:
- [ ] Given `add owner/repo -y` on a skills-only repo with Claude detected, every non-internal skill installs as its own entry for Claude with no prompts and exits 0; with no agent detected, they install for every agent within each entry's ceiling
- [ ] Given `-y` where an entry's target holds untracked files or another managed install, or its key is held by an install from another repository (e.g. `add gitlab:owner/repo -y` over a GitHub `owner/repo` install), that entry stops, what was in the way stays, the message names `--overwrite`, other entries install, and the command exits non-zero
- [ ] Given `-y --overwrite` with the same clashes, the untracked files are overwritten and the clashing managed install is removed with no prompt, the new install taking its key
- [ ] Given no terminal and no `-y`, `add owner/repo` exits non-zero without waiting on input, writes nothing, and names `-s/--skill`, `-a/--agent` and `-y`
- [ ] Given `add` run from within an AI agent (detected as Vercel detects it), "Agent detected — installing non-interactively" replaces the banner and it behaves as `-y`; given only `CURSOR_TRACE_ID` set, it behaves as an attended run
- [ ] Given a plugin carrying hooks under `-y`, it installs with its hooks and the summary lists them by name
- [ ] Given a terminal without `-y` or `--overwrite`, the clash prompts behave as today, and a deliberate cancel exits 0
- [ ] Given a bundle in which one member restricts to Claude, under `-y` with Claude and Cursor detected, it installs for Claude only; with no agent detected, it installs for Claude only
- [ ] Given a Claude install with Cursor detected, when it is re-added under `-y` (or from a detected agent caller), Cursor is added and Claude's copy stays; with no agent detected, every agent within the unit's ceiling is added
- [ ] Given `-y` where an entry's key is held by another entry from the same repository as a different unit (a skill declaring `foo` over the installed top-level plugin member `foo/`), that entry stops with the other install intact and the message names `--overwrite`, even when none of their files overlap; with `-y --overwrite`, the other entry is removed and the new install takes its key
