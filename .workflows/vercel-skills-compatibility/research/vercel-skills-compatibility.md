# Research: Vercel Skills Compatibility

Explores what it takes for agntc to be a like-for-like replacement for Vercel's `skills` CLI — anything built for their skills library installs through `npx agntc add` with the same source formats, flags, and behaviour — while keeping agntc's own formats and its `--plugin` bundling intact. Prompted by three inbox ideas from the 2026-06-09 e2e-fixtures testing session (non-interactive install flags, Vercel CLI cross-compatibility, a richer post-clone `add` intro), pulled together in discovery as one feature.

## Starting Point

What we know so far:
- **Core intent:** install skills built for Vercel's skills library directly into Claude Code (and Codex/Cursor) through agntc, swapping the binary — `npx skills add owner/repo` → `npx agntc add owner/repo` — and getting an equivalent install.
- **Constraint — don't break agntc's own systems.** In particular `--plugin`, which bundles a skills-only source as one unit. Vercel's CLI has no equivalent; it is the reason agntc exists. The owner has used it to install a large set of skills by one author that are designed to be installed individually through Vercel's CLI.
- **Already shared with Vercel's model** (per the compatibility seed): tagless source → HEAD, directory-basename identity, skills-only root → member menu (Vercel's one-level-into-`skills/` discovery). *(Amended 2026-10-05 — deep-dive-001 read Vercel v1.7.0: its identity is the frontmatter `name`, not the directory basename — selection, install-dir name and lock keys all use it; and container discovery now walks 3 levels. Only tagless→HEAD and skills-only→menu are shared as stated.)*
- **Unattended installs are in scope** as part of Vercel's `add` surface: `--agents` (the seed's name; Vercel's flag is `-a/--agent`, singular and variadic — deep-dive-001) pre-answering agent selection (still intersected with a unit's declared agent ceiling), `--yes`/`-y` with a precise definition of what it answers at each prompt, and a way to select collection members without a prompt. Open in the seed: interaction with auto-select, conflict resolution under `--yes`, error behaviour when a flagged agent is outside a unit's ceiling.
- **Pre-install summary is in scope**, also as part of Vercel's `add` surface. Vercel shows a connected tree after clone — source URL, repository cloned, "Found N skills", unit names, and a per-skill description. *(Amended 2026-10-05 — per deep-dive-001, v1.7.0 lists names and descriptions only for a single auto-selected skill, in the picker's description pane, under `--list`, and for well-known sources; a multi-skill repo shows only the count after "Found N skills".)* The ASCII banner half shipped already (`abfe6c9`, `src/banner.ts`); the post-clone information is what remains. agntc deliberately does not parse `SKILL.md` frontmatter (identity = directory basename), so a description line would be a scoped, read-only, display-only frontmatter read. Keep it sized to agntc's three agents, not Vercel's ~71-agent list (79 in v1.7.0 — deep-dive-001).
- **Two validation strands surface here** even though validation as a whole was left out of scope: Vercel rejects a skill whose frontmatter lacks `name` + `description` *(amended 2026-10-05 — per deep-dive-001 it skips that skill with a visible `⚠ Skipped` warning and installs the rest; only a repo with no valid skill at all fails)*, so the compatibility contract has to take a position on repos Vercel would refuse; and unattended installs remove the last human look before hook scripts land.
- **A defect rides along:** when updating something installed with `--plugin`, the out-of-constraint re-add advice omits `--plugin`, so following it fails. The owner flagged the exact behaviour may be slightly different — to be verified. Treated as part of this work ("fix partially-done paths along the way"), not a separate bugfix.
- **Reshape cue:** if the audit of Vercel's CLI turns up whole capabilities agntc has no equivalent for — installing once for every project rather than per project, or searching their directory — the work becomes several connected pieces and should be re-shaped then. The owner may also roadmap some extra work for later rather than have it ride along.
- **Out of scope by discovery:** the broader validation bucket, and the member-select wording idea (stays in the inbox as quick-fix material).
- Starting point is technical: audit the Vercel surface first, then map it onto agntc.

## First read — agntc's `add` line against Vercel's (2026-10-05)

Prior ground: the configless-install research (2026-06-04) reverse-engineered `vercel-labs/skills` @ v1.5.10. Its source-string superset: `owner/repo`, `owner/repo@skill`, `owner/repo/subpath`, GitHub `tree/<branch>/<path>` URLs, GitLab incl. nested subgroups, `github:`/`gitlab:` prefixes, SSH, local paths, `#ref` and `#ref@skill` fragments, source aliases, fallback to a direct git URL. Its `add` flags: `--skill`, `-a/--agent`, `-g`, `--all`, `--full-depth`, `-y`. *(Since read at v1.7.0 — see deep-dive-001 below; the `@`/`#` grammar and the flags above still hold, with more added.)*

Measured against agntc today:

- **`add` takes one flag.** `grep -rn "\.option(" src/ | grep -v "\.test\.ts"` → one hit, `src/commands/add.ts:914`, `--plugin`. No agent, skill-selection, yes, global, or list flags.
- **The `@` suffix means opposite things.** In agntc, `owner/repo@X` is a ref or a semver constraint (`^`/`~` → constraint, anything else → ref; `classifyRefOrConstraint`, `src/source-parser.ts`). In Vercel, `owner/repo@X` selects the skill named X, and a ref goes in a `#ref` fragment. A Vercel line `npx skills add owner/repo@some-skill` swapped to `agntc` is not refused — it is read as "clone at ref `some-skill`", which fails on the missing ref or, if a branch or tag of that name exists, installs the wrong thing. A collision, not a gap.
- **`owner/repo/subpath` shorthand is refused.** `grep -n "too many slashes" src/source-parser.ts` → line 365, error "too many slashes in source … — expected owner/repo". Vercel accepts it. (agntc reaches a subpath only through a `tree/<branch>/<path>` URL.)
- **A standing spec decision sits in the way of flag parity.** `grep -n "No install-command flags" .workflows/configless-install/specification/configless-install/specification.md` → line 52: "No install-command flags for type or unit selection, except the single narrow `--plugin` installer override … Unit selection from a collection is via interactive prompt or a source-string selector." The configless-install research recorded this as a deliberate reaction against Vercel's flag-heavy `add` (`--skill`, `-a`, `-g`, `--all`, `--full-depth`, `-y`). The carrier's "same source formats and flags" meets it head-on — a high-confidence decision of another work unit.
- An earlier investigation (update-check-fails-on-branch-ref, 2026-07-02) parked "`npx skills add nuxt/ui` resolving to the right subpath" as this idea's ground.

## Owner's framing — the method and what's open (2026-10-05)

- **The no-install-flags decision is open to reopening.** The owner is not against reopening it: the bar is that Vercel install lines work as expected. For each mismatch the paths are adapt agntc's rules, change them, or make both work.
- **Method:** work through everything Vercel's system can do, line it up against what agntc has built, and see what's left — in the owner's words, what falls out is what needs talking about.
- **`@` has to be given one meaning** (or a rule that reads it) — named by the owner as one of those things.

### `@` — the shape of the problem (preliminary, ahead of the Vercel audit)

What each tool puts after `@` today: Vercel (v1.5.10) — a skill name, with the ref in a `#ref` fragment and `#ref@skill` composing both. agntc — a semver constraint (`^`/`~`), an exact tag (`v2.0.0`), or any other ref such as a branch. agntc's own surfaces also emit `@`: the out-of-constraint footer's re-add advice prints `npx agntc add <repo>@<newest>` for an exact-pin user, so whatever `@` comes to mean reaches that advice too (and the `plugin-readd-defect` thread sits on the same line).

Option landscape as it stands (not exhaustive, pending what the audit finds):

1. **Vercel grammar wholesale** — `@` selects a skill, `#` carries ref/constraint (`owner/repo#^1.0`, `#v2.0.0`, `#main`). Every pasted Vercel line works; every agntc line already written (docs, READMEs, the footer's advice, habit) breaks or needs a deprecation path.
2. **Read the suffix by shape** — `^`/`~` ranges and semver-shaped tags stay versions; anything else selects a skill; `#` carries arbitrary refs. Common lines from both tools work. Cost: agntc's `@branch` form moves to `#branch`; the residual ambiguity is a skill whose name is version-shaped.
3. **Read the suffix against the repo** — clone, then treat `@X` as a skill if one named X exists, else as a ref. Chicken-and-egg: the ref decides what is cloned, so this means a default-branch probe first; and a repo with both a branch and a skill named X stays ambiguous.
4. **Separate grammars by entry point** — agntc's grammar by default, Vercel's under some compatibility switch. Fails paste-and-go unless the switch is automatic.

Lean at this point: (2) gets the most real lines working in both directions for the smallest break, but it hangs on facts the audit has to supply — notably what Vercel's `@skill` matches against. Vercel dedups skills by frontmatter `name`; agntc's identity is the directory basename. If Vercel's selector matches the frontmatter name, a selector that works in Vercel can miss in agntc even with `@` settled. *(It does — deep-dive-001: frontmatter `name` only, case-insensitive.)*

## agntc's own printed re-add advice — the `--plugin` defect, and a second one (2026-10-05)

`grep -rn "npx agntc add" src/ | grep -v "\.test\.ts"` → four advice sites (plus doc comments and `list`'s empty-state hint). None carries `--plugin`:

| Site | When it prints | Command printed |
|---|---|---|
| `src/summary.ts:355` (`renderOutOfConstraintSection`) | `update`, newer major outside a caret constraint | `npx agntc add <owner/repo>` |
| `src/update-render.ts:80` (`formatNewerTagsLine`) | all-mode `update`, exact-pinned group with newer tags | `npx agntc add <owner/repo>@<newest>` |
| `src/commands/update.ts:173` | single-key `update <key>`, exact pin with newer tags | `npx agntc add <key>@<newest>` |
| `src/clone-reinstall.ts:270` (`buildAbortMessage`) | derive-before-delete abort | `npx agntc remove <key> then npx agntc add <key>` |

- **The `--plugin` drop is confirmed, at every site.** The manifest records `type: "skill" | "plugin"` (`src/manifest.ts:18`) but not *why* — a structural plugin (`skills/` + `agents/`/`hooks/`) and a skills-only source bundled by `--plugin` both record `plugin`. Following the bare advice for a `--plugin` bundle re-detects the source as skills-only and takes the default collection-menu path. Code read (not run end-to-end): members key as `owner/repo/<member>`, distinct from the bundle's `owner/repo` key, so their files collide with the bundle's and the collision prompt offers "Remove owner/repo and continue" — following the advice to completion converts the bundle into separate members rather than upgrading it. The owner's recollection ("following it fails") is close: it doesn't error, it silently changes the install's shape or stops at a collision prompt.
- Observation: because a `--plugin` on a structure that already reads as a plugin is a redundant no-op under the configless-install spec (type agrees → no-op), advice carrying `--plugin` whenever the recorded type is `plugin` would not misfire on structural plugins. Material, not a fix decision.
- **Second defect — member-scoped advice is refused by agntc's own parser.** The single-key newer-tags site and the abort message print the manifest key, which for a collection member is `owner/repo/<member>`. Run against the parser: `npx tsx -e '…parseSource("owner/repo/member@v2.0.0")…'` → `ERROR: too many slashes in source "owner/repo/member" — expected owner/repo`; same for `owner/repo/member` bare. So for any collection member, those two printed commands cannot be run as printed. (The all-mode newer-tags line already uses the bare `owner/repo` — its doc comment notes it mirrors the single-key path "at group granularity" — so the two surfaces disagree.) This connects to the Vercel audit: accepting `owner/repo/subpath` shorthand, which Vercel does, would make these lines parse.

## Prompts `add` can show today (2026-10-05)

`grep -rnE "(select|multiselect|confirm|text)\(\{" src | grep -v "\.test\.ts"` plus the clack imports → the prompts on the `add` path:

1. **Collection member pick** — multiselect, nothing required (`src/collection-select.ts:34`). Shown for any collection, including the skills-only default.
2. **Agent pick** — multiselect over the author's declared agents or, with none declared, all known agents; detected agents pre-ticked; an empty pick is a deliberate "none" (`src/agent-select.ts:63`). Auto-skipped only when the author declared exactly one agent and it is detected (`src/agent-select.ts:39–47`).
3. **Collision with another managed install** — per colliding key: "Remove <key> and continue" / "Cancel installation" (`src/collision-resolve.ts:36`). Reinstalling the *same* key never asks — its files are nuked and replaced (`src/commands/add.ts:413–415`, `:775–778`).
4. **Unmanaged files in the way** — "Overwrite all" / "Cancel this plugin's install", then a second "Are you sure? These files will be permanently replaced." (`src/unmanaged-resolve.ts:37`, `:57`).

An unattended `add` has to answer all four; (3) and (4) are destructive — the only prompts whose "yes" deletes something.

## Who runs agntc unattended — and what happens to them today (2026-10-05)

**The owner's picture of the callers:** either the owner at a terminal, or an AI agent (Claude, or another agent) running `npx agntc add` mid-task. CI is possible but not what they imagine.

**What an agent gets today — measured.** Fixture: a skills-only collection (`skills/alpha`, `skills/beta`) added from a scratch project via `npx tsx src/cli.ts add ../coll`:

- From this Claude Code session's own shell (`test -t 0` → "stdin not a TTY"): `timeout 15 npx tsx …/src/cli.ts add ../coll` → `rc=0 elapsed=1s`, and `find proj -not -path '*/.git*'` shows nothing installed (no `.agntc/`, empty `.claude/`). The first prompt ("Select plugins to install") renders, reads end-of-input as a cancel, and the command exits **0 with nothing done and no message saying so**.
- Same with stdin explicitly closed (`</dev/null`): `rc=0 elapsed=0s`, nothing installed.
- With stdin held open but silent (`sleep 30 | timeout 12 …`): `rc=124` — it **hangs** until killed.

The exit-0 is by design for a human: agntc treats a cancelled prompt as a deliberate no-op (`throw new ExitSignal(0)` at the cancel sites, e.g. `src/commands/add.ts:385`, `:703`). For an agent caller the same design reads as success. So the agent case isn't only about missing flags — today an agent either hangs or gets a quiet success that isn't one.

**What changes when the unattended caller is an agent rather than a script:**

- **The caller can make choices — it just can't see a prompt.** An agent can pass whichever agents, skills, and conflict policy the user asked for. That makes flags that state a choice explicitly (which agents, which skills, what to do on a clash) carry more weight than a blanket "yes to everything", which mostly serves a human skipping prompts they would have accepted anyway.
- **The human's last look moves to the agent's permission prompt.** When Claude runs a command, the owner approves the command line. A line that states its choices (e.g. `--agent claude --skill foo`) is reviewable there; a bare `-y` hides what it will do, including the two destructive answers. This bears on the hook-scripts thread: the approval moment still exists, it just sees the command, not the prompts.
- **The caller needs to know what's in a repo before choosing.** A human reads the collection menu; an agent needs that information in output it can read before it commits to a selection — either a look-without-installing mode or a pre-install summary the agent can act on. Connects to the pre-install-summary thread.
- **Not-a-terminal is detectable.** Whatever the flag set ends up being, a run with no terminal and an unanswered choice has two broad options: stop with a non-zero exit naming the choice and the flag that answers it, or fall back to a default. The defaults are harmless for some prompts (agents pre-ticked by detection) and not for others (the two destructive ones).

**Lean recorded in conversation (a position, not a decision):** when an agent-driven install hits another install's files or untracked files in the way, stop and come back to the owner rather than replace silently — with an explicit override flag the owner then sees in the command they approve. Matching Vercel exactly gives the same install, but Vercel's "same install" includes quietly deleting what is in the way (deep-dive-001: conflicts are never prompted).

### Answers

**Version and drift.** 203 commits separate v1.5.10 (the configless-install read) from v1.7.0 (https://api.github.com/repos/vercel-labs/skills/compare/v1.5.10...v1.7.0). Material since then: `add` gained `--json`, `--subagent`, `--metadata`; malformed `SKILL.md` is now warned (`⚠ Skipped …`) instead of silently skipped (`40a859c`, 2026-07-21); container discovery depth 3 (`6eeafb7`); direct `SKILL.md`/archive URL sources; GitHub Enterprise via `GH_HOST`, Azure Repos; private-repo credential chain; `--skill '*'` excludes internal skills; `add` exits non-zero when a prompt can't run without a TTY (`a6a9507`, 2026-09-08); Notion integration (v1.7.0's only new feature over v1.6.0). On `main` after v1.7.0: Pi becomes a shared-directory agent, project `update` skips unchanged skills by hash, `-g` local installs recorded in the global lock, telemetry moves to `www.skills.sh/tele`. The Mintlify and Hugging Face providers are gone.

**Commands** (`src/cli.ts` and per-command files): `add` (aliases `a`, `i`, `install`), `use` (copy one skill to a temp dir and print a prompt, or launch claude/codex/sarvam-code with it; never prompts), `remove` (`rm`, `r`; `-g`, `-a`, `-s`, `-y`, `--all`), `list` (`ls`; `-g`, `-a`, `--json`), `find` (`search`, `f`, `s`; skills.sh search, live picker that installs on a TTY, `--owner`), `update` (`upgrade`, and `check` — an undocumented alias that runs the full update, not read-only; `-g`, `-p`, `-y`), `init` (writes a template `SKILL.md`), `experimental_install` (restore from `skills-lock.json` into `.agents/skills`), `experimental_sync` (install skills found in `node_modules`).

**`add` flags** (`src/add.ts` `parseAddOptions`): `-g/--global`; `-a/--agent <agents…>` (variadic, repeatable, no comma splitting, `'*'` = all 79 agents, unknown name → "Invalid agents" + exit 1); `-s/--skill <skills…>` (variadic, `'*'` = all non-internal); `-l/--list` (print available skills, exit 0); `-y/--yes`; `--copy` (copy instead of symlink); `--all` (= `--skill '*' --agent '*' -y`); `--full-depth`; `--json` (needs `-y`/`--all`; JSON array of per-skill results on stdout); `--subagent`, `--metadata` (Eve / telemetry). Parsing quirks read from code: unknown flags silently ignored; no `--flag=value` or combined short flags; a positional after a variadic flag is swallowed by it (`-s foo owner/repo` leaves no source). A source `@skill` is appended to the `--skill` list; `'*'` anywhere wins. Install method defaults to symlink, forced to copy when every target shares one skills dir.

**Source grammar — what `@`, `#` and subpaths select** (`src/source-parser.ts`):
- `owner/repo@X` — **`X` is always a skill selector, never a version.** `owner/repo@v1.2.0` selects a skill named "v1.2.0". The `@` must follow the repo name directly: `owner/repo/sub@x` is the subpath `sub@x`.
- `#ref` and `#ref@skill` — the ref lives in the fragment (split at first `#`, then first `@` inside it); a fragment skill overrides an `@skill`. Only parsed on sources that look like git.
- `owner/repo/sub/path` — subpath shorthand, accepted (`..` → "Unsafe subpath").
- Also: local paths, `github:`/`gitlab:` prefixes, GitHub `tree/<ref>[/<path>]` URLs (ref captured as `[^/]+`, so a branch containing `/` would mis-split), GitLab `/-/tree/`, Azure `_git` with `?path=`/`?version=`, SSH (type `git`), `https://…​.git`, hosted-artifact URLs (raw/codeload/archive/releases → download), `notion`, skills.sh packs (`https://skills.sh/p/<id>`), two aliases. **Any other http(s) URL not ending `.git` and not on github/gitlab is treated as a well-known endpoint, never cloned** — a self-hosted `https://git.example.com/g/r` without `.git` won't clone.
- Refs: only from `#ref`, a tree segment, or Azure `version`; applied as `git clone --depth 1 --branch <ref>`; full 40-hex SHAs work via a fetch fallback, abbreviated ones don't (`src/git.ts`). **No semver, range, constraint or latest-tag logic anywhere** — `update` re-fetches the same recorded ref.

**What a selector matches — the load-bearing answer.** `filterSkills` (`src/skills.ts`) compares the lowercased input by strict equality with the lowercased frontmatter `name` (the display-name fallback to the folder basename never fires, since every parsed skill has a name). **`@skill` and `--skill` match the frontmatter `name` only — case-insensitive, exact, no slug normalisation. The folder basename is not a match target.** Real case in Vercel's flagship repo: `vercel-labs/agent-skills/skills/react-best-practices/` declares `name: vercel-react-best-practices`; `skills/composition-patterns/` declares `vercel-composition-patterns`; skills.sh prints `npx skills add https://github.com/vercel-labs/agent-skills --skill vercel-composition-patterns` (https://skills.sh/vercel-labs/agent-skills/composition-patterns). No match → "No matching skills found for: X" + available list, exit 1. Partial match (`--skill a b`, only `a` exists) → installs `a`, drops `b` silently, exit 0. `use` is stricter (fails on ambiguity or a multi-skill source with no selector).

**Discovery** (`src/skills.ts`, `src/plugin-manifest.ts`): a skill is a `SKILL.md` with string `name` and `description`; anything else is skipped with `⚠ Skipped <path> — <reason>`; no valid skill at all → "No valid skills found…" exit 1. `metadata.internal: true` hides a skill unless requested by name or `INSTALL_INTERNAL_SKILLS` is set. Algorithm: root `SKILL.md` early-out (unless `--full-depth`); else root (1 level) plus `skills/`, `skills/.curated|.experimental|.system` and 30 hard-coded agent dirs, each walked 3 levels; plus paths from **`.claude-plugin/marketplace.json` and `.claude-plugin/plugin.json`** (skill dirs only — no agents/hooks routed); never below a found skill, never into `node_modules/.git/dist/build/__pycache__`, symlinked dirs not followed; fallback full recursive walk (depth 5). Dedup by exact frontmatter `name`, first in priority order wins.

**Agent targeting** (`src/agents.ts`, `src/installer.ts`, `src/detect-agent.ts`): 79 agents plus a `universal` pseudo-agent. **Identifiers: `claude-code`, `codex`, `cursor` — `--agent claude` is rejected.** 22 "universal" agents (including codex and cursor) read the shared `.agents/skills`. Project paths: claude-code `.claude/skills/`; **codex and cursor both `.agents/skills/`**. Global: canonical `~/.agents/skills/<name>`, plus a link in `~/.claude/skills` for claude-code; for codex and cursor the installer writes only `~/.agents/skills` though the README lists `~/.codex/skills/` and `~/.cursor/skills/`. Detection is machine-level (`~/.claude`, `~/.codex`, `~/.cursor` exist). Choice order: `--agent` → running inside an AI agent (via `@vercel/detect-agent`: targets that agent plus all universal agents, `yes` forced) → detection (0 detected: prompt, or with `-y` **all 79 agents**; 1 detected or `-y`: detected plus universal; 2+: picker, preselected from the last choice stored in the global lock).

**Install semantics.** Install directory = `sanitizeName(frontmatter name)` (lowercase, non-`[a-z0-9._]` runs → `-`), so `skills/react-best-practices/` installs as `vercel-react-best-practices/`. Default: canonical copy in `.agents/skills/<name>` (project) or `~/.agents/skills/<name>` (global), relative symlinks from each non-universal agent's dir. Copies the whole skill dir (excluding `metadata.json`, `.git`, `__pycache__`; `node_modules` included), **dereferencing every symlink with no containment check**. **Conflicts: never prompted** — the Installation Summary lists `overwrites:` and the existing dir is `rm -rf`'d and replaced. Two locks keyed by frontmatter name: global `$XDG_STATE_HOME/skills/.skill-lock.json` or `~/.agents/.skill-lock.json` (global installs only; v3; entry `{source, sourceType, sourceUrl, ref?, skillPath?, skillFolderHash, installedAt, updatedAt, pluginName?, …}`); project `./skills-lock.json`, meant to be committed (v1; entry `{source, sourceUrl?, ref?, sourceType, skillPath?, computedHash, …}`). **Neither records target agents, install mode, or a commit SHA.** `update` spawns `add <source>[/<folder>]#<ref> --skill <name> -y` with **no `--agent`**, so targets are re-detected at update time; v1.7.0 reinstalls every project skill each run. `remove` matches sanitized folder names and lock keys; without `--agent` deletes from every agent path.

**Non-interactive behaviour** (`src/add.ts`):

| Prompt | Pre-answered by | What `-y` answers |
|---|---|---|
| "Select skills to install" | `--skill`, `@skill`, `--all` | **all skills** |
| "Which agents do you want to install to?" | `--agent` | 0 detected: **all 79**; else detected + universal |
| "Installation scope" | `-g` (no explicit project flag) | project |
| "Installation method" | `--copy` | symlink |
| "Proceed with installation?" | — | yes |
| Eve prompts, Notion packs, find-skills offer | various | yes / all / skipped |

No TTY: `yes` is not implied; a reached prompt cancels and the CLI prints "Interactive prompt required but stdin is not a TTY. Nothing was installed." and "Use --agent <name> (or --agent '*') and -y to run non-interactively.", exiting **1**. A deliberate cancel on a TTY exits 0. **Inside an AI agent: `yes` is forced, banner replaced by "Agent detected — installing non-interactively"; with no selector every skill in the source installs.** CI env vars only tag telemetry. `update` under no-TTY/`-y` auto-detects scope and never removes upstream-deleted skills; `remove` skips its confirm under `-y`/`--all`/inside an agent.

**Pre-install display** (`src/add.ts`): banner; `Source: <url>` (with `@ <ref>`, `(<subpath>)`, `@<skillFilter>` suffixes); "Repository cloned"; `Found N skills` (+ any skip warnings); then one of `Skill: <name>` + description (single skill), `Installing all N skills` (`-y`/`*`), `Selected N skills: a, b` (named), or the picker with a description pane; `Installing to: …`; scope and method prompts; an **"Installation Summary"** note (per skill: canonical path, `universal:`/`symlink →`/`copy →`/`overwrites:` lines, 5 names then "+N more"); a **"Security Risk Assessments"** table (Gen/Socket/Snyk, public GitHub repos with telemetry on); "Proceed with installation?". After: "Installed N skills" and the outro "Review skills before use; they run with full agent permissions." Descriptions come from frontmatter `description`, terminal-escape-stripped. `--list` shows names and descriptions grouped by plugin.

**Safety posture.** YAML-only frontmatter (no `---js`); terminal-escape stripping on displayed metadata; lexical-only path guards (subpath `..`, discovery root, manifest paths, install names); symlinks in source repos dereferenced on copy with no containment check; size limits on downloads/archives but **none on git clones** (300 s clone timeout); git hardening (`ext::` rejected, protocol allowlist, no terminal prompt, LFS off). **No specific warning or confirmation for scripts or executables** — the only gate is "Proceed with installation?", skipped by `-y` or agent detection; the risk table is advisory. Telemetry: fire-and-forget GET on install/remove/update/find (install carries source, skills, agents, file map), sent only for public GitHub repos (checked by an anonymous GitHub API call) or non-GitHub sources, never for local; opt-out via `DISABLE_TELEMETRY` or `DO_NOT_TRACK`.

**Capabilities beyond project-scoped install from git/local** — each is its own module: global scope `-g` (high prominence: interactive `add` asks "Installation scope" whenever a target supports it; own lock; scope option on update/list/remove); the canonical `.agents/skills` store with symlink fan-out (the default); `find`/skills.sh search; `use`; `update`/`check`; well-known endpoints (`/.well-known/agent-skills/index.json`, schema `https://schemas.agentskills.io/discovery/0.2.0/schema.json`); skills.sh packs; direct `SKILL.md`/archive URLs; Notion (via the external `ntn` CLI); a skills.sh blob fast path for allowlisted owners (`vercel`, `vercel-labs`, `heygen-com`, `remotion-dev`, `zapier/connectors` — file contents come from `https://skills.sh/api/download/…`, not git); security-audit display; `--json`; Eve agent/subagents; `experimental_install`/`experimental_sync`; private repos, GHE, GitLab, Azure; auto mode inside an AI agent.

### Material — the line-up against agntc as it reads now

Where the two diverge, read straight off the answers and agntc's measured state above (synthesis, not decisions):

- **Identity is the deepest gap, not `@`.** Vercel selects, names the install directory, and keys its locks by frontmatter `name`; agntc by folder basename, and reads no frontmatter (configless-install spec, high confidence). So a pasted `--skill vercel-composition-patterns` can't match agntc's `composition-patterns` without reading frontmatter, and even a match installs to a different directory name than Vercel would. A Vercel-installed skill and the same skill installed by agntc land in two different directories. This undercuts the configless-install decision that agntc reads no frontmatter.
- **`@` settled on Vercel's side:** always a skill, never a version; refs in `#`; no semver concept to collide with agntc's constraints except through the `@` character itself. A shape-read of `@` (option 2 in the landscape above) would never misread a real Vercel line except one selecting a skill whose name is version-shaped — and Vercel's own `@` matches frontmatter names, which agntc doesn't read.
- **Agent identifiers differ** (`claude-code` vs agntc's `claude`) — a pasted `-a claude-code` needs mapping. **Cursor's project path differs**: Vercel installs Cursor skills to `.agents/skills/`, agntc to `.cursor/skills/` (`src/drivers/cursor-driver.ts:8`). Codex matches (`.agents/skills/`).
- **No TTY:** Vercel stops with exit 1 and names the flags to use; agntc exits 0 having done nothing (measured above). Vercel's behaviour is exactly the "stop loudly, name the flag" option.
- **Inside an AI agent:** Vercel goes the other way from explicit choices — forces `-y`, installs every skill to the detected agent plus every universal agent. That is the behaviour a pasted bare `npx skills add owner/repo` produces when an agent runs it.
- **Conflicts:** Vercel never asks and overwrites; agntc asks (collision with another install; unmanaged files, double-confirmed).
- **Symlinks in source repos:** Vercel copies through them with no containment check; agntc already blocks symlink escapes (`copy-safety.ts`). agntc is stricter here.
- **Install mode:** Vercel defaults to a canonical copy plus symlinks; agntc copies per agent. Invisible to the skill's behaviour; visible on disk and to a later Vercel `update`/`remove`.
- **Locks:** Vercel's committed `./skills-lock.json` and global lock record neither agents nor commits, and have no constraint concept; agntc's `.agntc/manifest.json` records agents, ref, commit and semver constraint. agntc has no reader for either Vercel lock.
- **Claude plugin manifests:** Vercel finds skills through `.claude-plugin/marketplace.json` and `plugin.json`; agntc has no reader — `grep -rln "claude-plugin\|marketplace.json" src | grep -v "\.test\.ts"` → nothing. A repo whose skills are only reachable via a marketplace manifest would be found by Vercel and missed or mis-detected by agntc's structural detection.
- **Scope:** Vercel has global installs as a first-class, prominent option; agntc is project-only. The discovery reshape cue named exactly this.
- **Unknown flags** are silently ignored by Vercel; a pasted line carrying a flag agntc doesn't know will be refused by commander unless agntc chooses otherwise.

Notes on the dive's other opened lines (not carried as threads): whether a folder-name selector fails on Vercel's blob fast path, and whether forced `-y` inside Claude Code installs everything, are confirmable by a sandbox run of Vercel's CLI — the code reading is consistent and nothing turns on the confirmation. How many listed repos contain skills Vercel would skip sizes the frontmatter-validity question; small value while agntc installs them regardless. Whether Codex and Cursor read `~/.agents/skills` globally matters only if global scope is pursued. The skills.sh pack index (`/p/<id>`), the tree-URL branch-with-`/` split, and whether Vercel's GitHub privacy probe fires under telemetry opt-out are Vercel's own concerns. Whether Vercel has an upstream proposal for version ranges was not searched — relevant to the `@` thread if it exists (a future `#^1.0` would align with option 1 or 2 above).

## Does agntc still have a reason to exist? — the owner's workflows against Vercel v1.7.0 (2026-10-06)

**The owner's question:** agntc was built to install the owner's workflows — a set of skills and agents that only work installed together as one unit — which Vercel's library couldn't do. Has Vercel closed that gap? And if agntc is still needed, is there a clear road to keeping its benefits while supporting everything Vercel does?

**The workflows repo, measured** (`~/Code/agentic-workflows`):

- `find skills -mindepth 1 -maxdepth 1 -type d | wc -l` → 38 skill dirs; `find agents -mindepth 1 -maxdepth 1 | wc -l` → 34 agent files; no `hooks/`, no `.claude-plugin/`; `agntc.json` → `{"agents": ["claude"]}`.
- Frontmatter check — `for f in skills/*/SKILL.md; do head -20 "$f" | grep -q '^name:' && head -20 "$f" | grep -q '^description:' || echo "$f"; done` → 32 of 38 have a `name` but **no `description`** (internal, non-invocable skills: e.g. `workflow-research-process` carries `name`, `user-invocable: false`, `allowed-tools`). Folder name equals frontmatter `name` for all 38.

**What Vercel v1.7.0 would do with it** (from deep-dive-001's reading of the code — not run):

- **Installs 6 of the 38 skills.** The 32 without a `description` are skipped with `⚠ Skipped … missing required frontmatter field(s)` — Vercel's validity rule, applied to the owner's own repo, drops most of it.
- **Installs none of the 34 agents.** Vercel installs only skill directories; agents, hooks and commands are never routed, even when found through a Claude plugin manifest.
- **No unit.** Each installed skill is its own lock entry, updated and removed independently; there is no record that they belong together and no way to update them as one.
- **Ignores the author's Claude-only restriction.** Vercel has no author-declared agent ceiling; `-y` fans out to the detected agents plus every agent reading `.agents/skills` (Codex, Cursor, …), and inside an AI agent `-y` is forced.
- **No version ranges.** Same-ref refresh only; agntc's semver constraints have no counterpart.

So the gap is not closed — Vercel's model is "a repo is a bag of independent skills", and on the owner's workflows it would produce a partial, unusable install. agntc's reason to exist stands on four things Vercel has none of: units (bundles of skills + agents + hooks, including `--plugin` bundling of skills-only sources), the author's agent restriction, semver constraints with constrained update, and a lenient validity posture (no frontmatter gate). Plus copy-safety (symlink-escape blocking), where Vercel is looser.

**Is there a clear road? — synthesis, not a decision.** The two tools sit on different axes. Vercel's surface is breadth on the "individual skills" axis: many agents, project/global scope, grammar breadth, search, `use`, published indexes. agntc's distinctive value is the "unit" axis, which Vercel doesn't occupy. Most of Vercel's surface is additive for agntc — new source forms, flags, agent mapping, scope, non-TTY behaviour — and does not touch bundling. The points where "everything Vercel does" presses on what agntc guarantees are few and nameable:

1. **Picking a skill out of a unit.** Vercel's `--skill x` / `@x` picks any skill from any repo. agntc keeps a plugin whole because a partial install breaks it. A pasted `--skill` aimed at a repo agntc reads as a unit is the one place Vercel's selection collides with bundling head-on.
2. **The validity gate.** Matching Vercel's "skip skills without name + description" would drop 32 of the owner's own 38 skills. agntc reading frontmatter for *matching* (the identity thread) is a different thing from *gating* on it.
3. **Author agent restriction vs `--agent '*'` / agent-forced `-y`.** Vercel's defaults fan out to every agent; agntc honours the author's ceiling.
4. **Unattended defaults.** Vercel's `-y` installs every skill and replaces whatever is in the way without asking; agntc asks today.
5. **`@` and identity** (their own threads) — grammar and naming, not guarantees; they decide whether pasted lines work, not whether bundles survive.

None of these forces giving bundles up; each is a place where agntc either follows Vercel or keeps its own rule, and in each the "keep" side is a rule agntc already has.

**What the run found that the code reading did not:**

1. **A skill's own `agents/` folder breaks it.** `src/type-detection.ts:144–155`: a directory with `SKILL.md` *and* an asset dir is a plugin — "SKILL.md found alongside asset dirs — treating as plugin, SKILL.md will be ignored". Real skills carry `agents/` folders for two unrelated reasons: OpenAI's `agents/openai.yaml` skill-metadata convention (`find … -path '*/agents/*' -name '*.yaml' | sort | uniq -c` → 71 `openai.yaml` files across the ten repos), and skill-local helper prompts the skill itself reads (`skill-creator`'s `analyzer.md`/`comparator.md`/`grader.md`; `motion-graphics`'s `builder.md`/`director.md`/`finalize.md`). agntc drops the `SKILL.md` and copies those files into `.claude/agents/` as if they were Claude subagents — for remotion, twelve entries all pointing at one overwritten `openai.yaml`. Skill dirs carrying an `agents/` subdir: 61 of 258 across the ten repos (mattpocock 38/38, remotion 12/12, caveman 7/28, hyperframes 2/40, anthropics 1/20, azure 1/86, the rest 0). The warning is printed (15 times across three runs) but every run ends "Installed …" with exit 0 — an agent caller reads success.
2. **Category folders hide whole collections.** `mattpocock/skills` nests every skill one level down under category folders. agntc's skills-only read looks one level into `skills/`, finds category dirs that aren't units, and ends with an empty pick that reads as a cancel. Vercel walks containers 3 levels deep. And were agntc to reach them, all 38 carry `agents/openai.yaml` — they would hit finding 1.
3. **A bare add installs a different version than Vercel.** agntc resolves the latest semver tag (5 of 10 repos had one); Vercel always installs the default branch HEAD. For a pasted bare line, "the same install" is not the same content wherever the default branch has moved past the last tag.
4. **Repos that are plugins to agntc are bags of skills to Vercel.** `azure-skills` (skills + hooks) and `caveman` (skills + agents) install as one unit with hooks/agents under agntc — arguably the richer install — but a pasted `--skill x` aimed at either is the pick-from-a-unit collision in the wild, not just in principle.
5. Lesser: Vercel's scan of root-level and agent-dir skills (`template/`, `.agents/skills`, `.claude/skills`) finds skills agntc doesn't — in these two repos, a template and the repo's own development skills.

Findings 1 and 2 sit on ground the configless-install spec decided (structure → type: `SKILL.md` alongside asset dirs → plugin; collection membership one level down).

**Leaderboard shape (observation, from the fetched page's summary, approximate):** besides git repos, `open.feishu.cn` — a well-known-endpoint site, not a git repo — holds roughly 26 of the top ~70 leaderboard positions (rank 19, ranks 20–40 folded as "+21 more", and ranks 42, 44, 48, 58). agntc has no way to install from a well-known endpoint, so a large share of the most-installed skills can't be reached by a git-only installer at all. Material for the capability-gaps thread.
